Pipeline Overview

The six-stage gating journey
"Each stage of the Ontology Pipeline prepares us for the next stage of building and provides a repeatable and measurable process for organizing information and knowledge."

Semantic knowledge systems (taxonomies → ontologies → knowledge graphs) have become the substrate for reliable AI: RAG grounding, entity management, information retrieval. Yet most organizations build them as a black box — no way to scope, estimate, or measure the investment.

Talisman's answer, derived from Library and Information Science (LIS) workflows, is to codify the build into six ordered, measurable stages. Each stage produces a concrete artifact that the next stage consumes, so the whole system can be scoped, staffed, priced, and incrementally validated — "positioned as both a product and a unique domain of expertise."

The anti-pattern she names: relying on out-of-the-box public taxonomies (e.g. Google Product Taxonomy) produces "homogenous knowledge ecosystems — a cookie-cutter approach that fails to meet the needs of a domain or business."

Stage-by-Stage Detail

STAGE 1Controlled vocabulary
"A controlled vocabulary deliberately stays small and pragmatic: it is the approved set of words and the governance that keeps them stable."

Work to do

  1. Purpose and scope — what decisions the vocabulary supports (search, tagging, analytics, routing); state in scope / out of scope explicitly "so the effort does not sprawl."
  2. Sources — where the words come from (style guides, ontologies, systems, logs), with provenance recorded per term.
  3. Style guide — five decisions: capitalization (sentence vs Title Case), abbreviations (spell out, acronym as alternative label), number (singular unless inherently plural), multi-word punctuation (spaces / hyphens / camelCase), word order (natural vs inverted for sorting).
  4. Terms — one preferred term per concept, alternative + hidden labels (e.g. catching the misspelling "Reprot"), and a definition in genus–differentia form ("X is a Y that Z").

Prevents: synonyms and near-duplicates propagating through everything downstream.

STAGE 2Metadata application profile (MAP)
"A metadata application profile (MAP) is, at its core, a declaration of the metadata terms an organization uses, how it uses them, and the constraints that apply in specific contexts."
  • Choose the Dublin Core elements each record type needs; per element declare obligation (required / recommended / optional), max occurrence, encoding (free text, ISO 8601 date, controlled-vocabulary value, IRI), and guidelines.
  • Build the systems crosswalk: which field in which system holds each element (e.g. profile title ↔ DMS "document title" ↔ Jira "summary" ↔ catalog "dataset name").
  • Metadata elements fall into structural (machine readability), descriptive (context), administrative (maintenance/lineage) — the essay adds provenance and social as extensions.

Prevents: entity-value chaos; the MAP is the "architectural blueprint" the taxonomy later fills with material.

STAGE 3Taxonomy
"Metadata schemas serve as architectural blueprints for the taxonomy, while controlled vocabularies provide the material from which we construct it."
  • Write use cases first (problem → how the taxonomy solves it → priority → owner).
  • Define a coverage model: what topics, how deep, what granularity, what comparable orgs/standards cover.
  • Create concept scheme(s) and place every approved term with its parent — or document why it's excluded.
  • Every parent edge must pass the Is-a test.

Design decisions the essay flags: how many levels; granularity; localization; whether the CV stays alive after deployment; how new terms enter. Validation should follow ISO 25964-1/2 and ANSI/NISO Z39.19.

Prevents: "the introduction of faulty logic, even within a base structure like taxonomy, can lead to the proliferation of errors throughout semantic knowledge systems."

STAGE 4Thesaurus
"Beyond the taxonomic structure, a thesaurus adds skos:related (associative), and joins across concept schemes through the mapping properties."

Adds what a pure hierarchy cannot say:

  • Associative relations (skos:related) — e.g. Under Review ↔ Compliance category.
  • Scope notes, examples, editorial and history notes.
  • Mappings to outside vocabularies (interoperability; classic BT/NT/UF terminology comes from this tradition).
  • Collections — groups for display, never hierarchy; ordered or not (e.g. a lifecycle list Draft → Under Review → Active → Deprecated).
  • Notation codes (e.g. WS-01) and optional SKOS-XL labels (labels as addressable entities with their own provenance).

Why taxonomy → thesaurus before ontology

"it is the crucial first step toward building a semantic, ontology-based knowledge management system."

STAGE 5Ontology (CBox · TBox · ABox · Check)
"The CBox comes first, which surprises most people who expect to start with classes and properties. The CBox is the administrative and governance layer."
CBoxTBoxSHACLABoxCheck
  • CBox (before any axioms): competency questions, the three namespaces (concept / schema / individuals), the ontology's own Dublin Core record (title, description, creator, license, rights, version in MAJOR.MINOR.PATCH), and the owl:imports declarations for SKOS and each reused standard.
  • TBox: reuse standards before defining custom terms; then classes (hierarchy first — "make a class from a concept / promote"), then properties.
  • Label-and-comment rule (verbatim): "The label and comment are written before the axioms — if a definition cannot be stated clearly, the concept boundary is not yet understood well enough to model."
  • The thin OWL frame + SHACL: the OWL layer stays deliberately thin (typing, domains, transitive/functional/inverse declarations). Rules that classes and properties cannot state live in SHACL shapes.
  • Shape definition (verbatim): A shape "picks a class, optionally a condition, and then a path of one or two properties whose values must be of a class or carry a value, at least and at most so many times. The Check applies every shape to the test ABox and reports each individual that breaks one."
  • ABox (verbatim): "Before deploying an ontology, build a representative set of ABox instances that exercises every class, every property, and every constraint available in the TBox."
  • Check (verbatim): "Populate a test ABox early, and run an RDFS-aware inference engine over it before you ever introduce OWL axioms. The errors that surface at the RDFS level are the cheapest to fix."
STAGE 6Knowledge graph
"A competency question is a natural-language question that the knowledge graph must be able to answer. It is not a vague business objective or a KPI. It is a question with a definite answer that the graph either can or cannot return."
  • Run SPARQL over everything stages 1–5 built — one query per competency question; the graph is "essentially a knowledge management tool" and the pipeline's visualization layer.
  • Graph-reading conventions (verbatim): solid arrows = hierarchy (rdfs:subClassOf, skos:broader, rdf:type); dashed = properties; dotted = scheme membership and term definition.
  • Exports: Turtle, N-Triples, JSON-LD, spreadsheet CSV.

Reuse principle

"each class and property carries the book's reason for it" — define a custom term only where no standard fits, and align it (e.g. producesArtifact aligned to prov:generated).

Suggested Study Path

  1. Read §1–§3 for the argument and stage mechanics.
  2. Open the Studio project 1 and walk stages 1→6 in order, reading each "line from the book" and running each stage's checklist; edit nothing yet.
  3. Read §4 alongside it, then export the Turtle (each stage prints "See the RDF") and read it — the same content in three serializations.
  4. Re-answer the eight competency questions from §6 by hand, then run them in the Studio's Query tab.
  5. Open project 2 (music tourism) and verify you can predict the shape of each stage before opening it — that is transfer of the method.
  6. Buy the book (links below) for the prose and full chapter checklists; the companion site is interactive, not the text.
